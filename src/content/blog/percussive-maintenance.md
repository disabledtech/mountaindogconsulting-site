Anyone who lived with an analog TV remembers the only fix that ever worked on a snowy picture: smack it. Open palm, the side of the cabinet, sometimes the top. A loose tube socket reseated; an oxidized contact came back to life; the picture cleared. Engineers had a half-joking name for the technique — *percussive maintenance* — and the appeal was that it took no diagnostics and no expertise. The TV had wedged; you hit it; the TV came back.

I've spent the last few weeks building the modern equivalent. The deflating discovery is that the smack is now a software-engineering project.

Here's the case. I sometimes drive my MacBook by voice. Voice Control is one of the input paths, and the keyboard isn't always within reach. Every so often, something snags — Voice Control stops responding, or Siri's panel opens and refuses to dismiss, and the only way to recover the machine is to press Escape. Which would be fine, if pressing Escape were available to me. It isn't always. And while there's nothing wrong with asking someone for help, the computer should have its own way out — the same way every other piece of mission-critical infrastructure does. My desktop machine has a handful of rescue paths, the bluntest being a hard power cut. The MacBook needed one too.

So the smack has to come from somewhere else. The phone, which is usually within earshot. Or the home automation system that already runs my house. I've got both of those wired up, and the obvious-looking design — phone tells Home Assistant to SSH into the Mac and run a script that presses Escape — turns out to be wrong.

Apple makes it deliberately hard to drive the GUI from an SSH session, and there's no way around this without fighting the platform's security model on its home turf. The system that does the gating is called TCC — Transparency, Consent, and Control — and it attaches its permission grants to specific binaries and to the *origin* of the request. The grant that lets a script press a key on the desktop when you double-click it does not transfer cleanly when the same script is invoked from sshd. Sometimes it works. Often it doesn't. The clearest statement on this comes from Apple's own DTS — Developer Technical Support — on the [Apple Developer Forums](https://developer.apple.com/forums/thread/765060): *"Running GUI code in an SSH session is always a bad idea."* Quinn, an Apple DTS engineer, said it in 2024.

The failure mode is the part that makes this so easy to get wrong: the SSH session returns exit code 0, the script reports success, the Mac sits there with its panel still up. You have a recovery path that passes every diagnostic you'd think to write, except for the one that matters — did Escape actually get pressed.

The design that works moves the GUI work out of the SSH session entirely. SSH does only one thing: touch a file. (`touch`, the Unix command, just bumps a file's modified-time stamp, creating the file if it doesn't exist. The contents don't matter; what matters is that something changed.) A small background process already running inside my logged-in session — a *LaunchAgent*, which is macOS's mechanism for keeping a program alive in your user session and reacting to things like a file change — watches that file and does the actual keystroke. The boundary carries only a signal. The action happens locally, where TCC believes it.

The chain on my desk now runs through five layers. I say "Hey Siri, rescue MacBook" to my iPhone. The phone Shortcut hits a Home Assistant webhook. The webhook fires a shell command that SSHes into the Mac with a tightly scoped key that's only allowed to invoke one script. The script does nothing but `touch ~/.rescue-trigger`. The LaunchAgent, watching that path, runs the actual rescue — `killall Siri`, then `osascript` to press Escape, then a small sanity log line. Five layers, for the moral equivalent of hitting the side of the cabinet.

The pattern is general. Any time an assistive automation has to act on the user's behalf across a trust boundary — a phone telling a desktop to dismiss a screen, a watch telling a tablet to advance a slide, a home automation telling a kiosk to wake up — the temptation is to make the boundary itself carry the action. The SSH command runs the keystroke. The API call moves the mouse. The webhook does the work. That path fights the platform's security model, and the platform almost always wins. The robust shape is the inverse: let the boundary carry a signal only, and have something inside the boundary, already trusted by the platform, respond to the signal. The trick is small. The framing is the load-bearing part. Stop trying to extend the user's session across the boundary; have something inside the session listening.

There's a specific reason this lands harder for an assistive-technology (AT) audience than for a general-purpose developer audience. When the input modality is single-channel — voice, eye gaze, sip-and-puff — the cost of a flaky rescue path isn't theoretical. It's "the computer is unusable until somebody else gets home." This is the shape of the world when you build for single-channel input as the load-bearing constraint: layered fallbacks become normal, the hard power cut is one of the rescue paths in your toolkit, and you think about recovery the same way you think about backups — multiple, tested, and independent.

Designing for the platform's actual permission model, not the imagined one, is the difference between a recovery system that works at 11pm on a Sunday and one you discover doesn't work at the moment you needed it. The hardening that makes the smack hard is the same hardening that protects the device from a hostile network. Both are doing real work. But the consequence of getting the rescue path wrong falls on a narrower group of users than the people designing the hardening tend to imagine — and that's the group I write for.

The smack-the-TV image is doing more work than it looks like at first. The reason percussive maintenance was a real category is that even an analog TV had failure modes its designers hadn't fully imagined, and the user needed a recovery path that didn't require understanding what had gone wrong. We still need that. The shape of the smack has changed — five layers of indirection instead of a flat palm — but the requirement is unchanged. The platform won't always reach the user. Build the path that lets the user reach back.
